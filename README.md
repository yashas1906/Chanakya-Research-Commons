# Chanakya Research Commons (CRC)

> **DMW (Data Mining & Warehousing) course project**, Semester 5, Chanakya University. Submission: 28 Nov 2026.
>
> A research platform for the university's six schools: a shared library, discussions, one search box over
> papers, people and posts, recommendations, a research assistant that cites its sources, and an admin
> dashboard on a star-schema data warehouse. Built on PostgreSQL 16 + pgvector, MinIO, a local LLM (Ollama),
> FastAPI and Next.js, with real literature from OpenAlex, arXiv and RSS feeds.

## 1. Project Overview

Chanakya Research Commons serves students, faculty, researchers and administrators across the six schools:

- **SAHSS**: School of Arts, Humanities and Social Sciences
- **SBS**: School of Biosciences
- **SOE**: School of Engineering
- **SLGPP**: School of Law, Governance and Public Policy
- **SMS**: School of Management Sciences
- **SMNS**: School of Mathematics and Natural Sciences

What it does, and the technique behind each part:

1. **Ingestion and deduplication**: papers from OpenAlex and arXiv and articles from 14 RSS feeds, stored raw in
   a MinIO data lake first, loaded in incremental batches, and merged across sources with MinHash LSH.
2. **Unified hybrid search**: semantic vectors (pgvector HNSW) and full-text search (`tsvector` + GIN) combined
   by Reciprocal Rank Fusion, over four panels: library, open literature, people, discussions.
3. **Library and community**: saves, collections, private notes, posts filed under research domains, threaded
   comments, votes, follows, and a "Best" feed ranked by follows and profile similarity.
4. **Recommendations**: co-save collaborative filtering blended with content similarity; "members who saved
   this also saved" from FP-Growth association rules with co-save and similarity fall-backs.
5. **Trends and moderation**: sliding-window topic spike alerts and Isolation Forest spam flags, reviewed by
   administrators.
6. **Research assistant (RAG)**: chunk-level retrieval with a similarity refusal gate and a local LLM
   (`llama3.2:3b`) that cites every claim.
7. **Admin dashboard**: a star-schema warehouse with engagement, topic, collaboration and drill-down views;
   FP-Growth / FP-Max topic bundles; Ward-clustered researcher archetypes; member, post and holdings management.

## 3. DMW Core Concepts & Feature Mapping

| Project feature | Implementation | Core DMW concept |
|---|---|---|
| **F1 Members** | Roles, profiles embedded into 384-d vectors (re-embedded on edit), member and topic follows | Vector representation, relational modelling |
| **F2 Feed** | "Best" = 2·followed author + 1.5·followed domain + cos(post, profile); posts filed under 32 fixed research domains | Content-based filtering, social graph weighting |
| **F3 Library** | Shared library with save counts, collections, private notes, save by DOI / arXiv / URL, admin holdings | Entity consolidation, relational junctions |
| **F4 Ingestion** | OpenAlex, arXiv, RSS → raw JSON/XML in MinIO → incremental, cursor-based batches every 6 h | Data lake, ELT, incremental loading |
| **F5 Deduplication** | 128-perm MinHash on word 3-shingles + LSH 0.5, verified by shingle/title Jaccard or embedding cosine ≥ 0.93, union-find merge | Locality-sensitive hashing, entity resolution |
| **F5 Authority** | PageRank (α = 0.85) on the citation graph → prestige tier, tie-breaks | Link analysis, graph centrality |
| **F5 Hybrid search** | RRF: 1/(60 + semantic rank) + 1/(60 + keyword rank) + w·PageRank percentile, w = 0 (tuned on dev queries) | Information retrieval, rank fusion |
| **F5 Query expansion** | Topic rules with lift ≥ 1.5 suggest related searches | Association mining |
| **F6 Recommendations** | z(co-save CF) + 0.5·z(0.7·profile + 0.3·saved-centroid similarity); cold start = profile only | Hybrid collaborative + content filtering |
| **F6 Also saved** | FP-Growth rules over member libraries (support ≥ 2 members) → co-saves → similar papers | Market-basket analysis, FP-Growth |
| **F6 / F9 Topic bundles** | FP-Growth and FP-Max over paper topic baskets per school | Maximal frequent itemsets |
| **F9 Researcher archetypes** | Ward agglomerative clustering + silhouette, tertile trait rules | Hierarchical clustering, profiling |
| **F7 Trends** | 7-day count vs 30-day weekly rate, ratio ≥ 1.5 and ≥ 5 events | Stream mining, change detection |
| **F7 Spam** | Isolation Forest on log post count, log mean gap, mean votes → admin review queue | Unsupervised anomaly detection |
| **F8 Assistant** | ~2 abstract chunks per paper, top-4 cosine retrieval, refusal below 0.32, cited answers from a local LLM | Retrieval-augmented generation, dense retrieval |
| **F9 Warehouse** | Date, member, topic, paper dimensions; research-activity and school-collaboration facts; drill-down | Dimensional modelling, star schema, OLAP |

## 4. Database Design & Schema Architecture

The database `chanakya_commons` runs in PostgreSQL 16 with `pgvector` and `pg_trgm`. DDL: `db/schema.sql`;
changes since then: `db/migrations/002–009` (idempotent, applied by `db/apply_migrations.py`).

### 4.1 Operational / OLTP Schema (`public`)

```
users (profile_embedding, role, department = school, is_synthetic, is_flagged_spam, spam_score)
  ├── user_follows (follower_id, followee_id)
  ├── topic_follows (user_id, topic_tag)              topic or research domain
  ├── collections (collection_id, user_id, name)
  ├── library_saves (user_id, paper_id, collection_id, private_notes)
  │        │
  │        ▼
  │    papers (canonical_title, abstract, authors, embedding, search_tsv, minhash_signature, pagerank_score,
  │            save_count, in_chanakya_library, item_type paper|article, created_by)
  │      ├── paper_sources (source_name, external_id, source_url, raw_minio_path)   one row per source record
  │      ├── paper_citations (citing_paper_id, cited_paper_id)
  │      ├── paper_chunks (chunk_index, chunk_text, chunk_embedding)                for the assistant
  │      └── paper_merges (canonical / merged record audit)
  │
  ├── posts (title, body, tags = research domains, attached_paper_id, post_embedding, search_tsv, upvote_count)
  │     ├── comments (parent_comment_id → threads)
  │     └── post_upvotes (user_id, post_id, value ±1)
  │
  └── activity_events (event_type, target_id, topic_tags, occurred_at)
system_alerts (topic_spike | spam_account) · ingestion_state (cursors) · ingestion_runs (audit)
```

### 4.2 Data Warehouse / OLAP Schema (`dw` star schema)

```
              dim_date (date_key, full_date, year, quarter, month, week_of_year, academic_semester)
                                   │
  dim_member ─────── fact_research_activity ─────── dim_topic (topic_name, parent_cluster)
  (role, school,     (date, member, topic, paper:    │
   is_active)         saves, posts, comments,        dim_paper (title, year, primary_source,
                      upvotes, views)                           pagerank_tier)

  fact_dept_collaboration (date_key, source_department, target_department, interaction_type, interaction_count)
  views: vw_paper_topic_baskets (FP-Growth / FP-Max) · vw_researcher_profiles (clustering)
```

### 4.3 Vector & Indexing Strategy

```sql
-- HNSW approximate nearest-neighbour indexes (cosine) on every embedding column
CREATE INDEX idx_papers_embedding ON papers       USING hnsw (embedding vector_cosine_ops);
CREATE INDEX idx_chunks_embedding ON paper_chunks USING hnsw (chunk_embedding vector_cosine_ops);
CREATE INDEX idx_users_embedding  ON users        USING hnsw (profile_embedding vector_cosine_ops);
CREATE INDEX idx_posts_embedding  ON posts        USING hnsw (post_embedding vector_cosine_ops);

-- GIN indexes for English full-text search (title weight A, abstract weight B)
CREATE INDEX idx_papers_tsv ON papers USING GIN (search_tsv);
CREATE INDEX idx_posts_tsv  ON posts  USING GIN (search_tsv);

-- B-tree indexes for time-window queries and joins
CREATE INDEX idx_events_time ON activity_events (occurred_at DESC);
```

## 5. Data Pipeline & Ingestion Engine

### 5.1 Stage 1: Seed corpus (`seed_database.py`, `improve_data.py`)

- **Real literature**: OpenAlex works for 24 research topics (four per school) with abstracts, plus arXiv
  preprints; raw responses archived to MinIO (`raw-ingestion/...`) before parsing.
- **Embeddings**: `sentence-transformers/all-MiniLM-L6-v2` (384-d) for papers, abstract chunks, member profiles
  and posts. MinHash signatures (128 permutations) stored per paper.
- **Synthetic community** (fixed seed): 60 members across 6 schools and 4 roles, collections and saves, 600
  posts, about 2,000 threaded comments, votes, follows and six months of events. `improve_data.py` gives
  realistic names, comments and votes; `fix_post_papers.py` attaches posts to papers on their author's topics.
- **Planted ground truth**: 30 near-duplicate papers, 5 spam accounts (120 burst posts), and 3 topic spikes
  (graph neural networks, CRISPR gene editing, data privacy law). `evaluation/build_ground_truth.py` rebuilds
  `evaluation/ground_truth.json` from these rules (never from detector output).

### 5.2 Stage 2: Entity resolution, PageRank & star schema ELT (`run_dw_elt.py`)

```bash
python data_pipeline/run_dw_elt.py
```

1. **Entity resolution** (`dedup.py`): MinHash over word 3-shingles of title + abstract, `MinHashLSH(threshold=0.5)`.
   Each candidate pair is verified (shared DOI / arXiv ID, or shingle Jaccard ≥ 0.5 with title word Jaccard ≥ 0.4
   or embedding cosine ≥ 0.93). Verified pairs are grouped with union-find and **merged** into one canonical
   record: sources, saves, notes, posts, citations and events move to it, and each merge is logged in
   `paper_merges`. Predictions go to `evaluation/predicted_duplicates.json`.
2. **PageRank**: NetworkX `pagerank(alpha=0.85)` over `paper_citations` → `papers.pagerank_score`.
3. **Star schema**: `dim_date` (with academic semester), `dim_member`, `dim_paper` (High / Medium / Low PageRank
   tier at the 80th and 40th percentiles), `dim_topic` (Ward agglomerative clustering of topic centroids into four
   named clusters), `fact_research_activity`, `fact_dept_collaboration`.
4. **Alerts**: topic spikes and spam accounts are scanned and written to `system_alerts` for the admin queue.

### 5.3 Stage 3: Incremental ingestion & scheduled refresh (`ingest.py`, `scheduler.py`)

```bash
python data_pipeline/ingest.py                      # next batch from OpenAlex, arXiv and RSS, then entity resolution
python data_pipeline/ingest.py --sources rss        # articles only
python data_pipeline/dedup.py --dry-run             # report duplicates without merging
python data_pipeline/scheduler.py --once            # one refresh cycle: ingest + run_dw_elt.py
python data_pipeline/scheduler.py --interval-hours 6
docker compose --profile scheduler up -d scheduler  # the same, as a container
```

- **Sources**: OpenAlex, arXiv (3 s between calls, as arXiv asks) and the 14 feeds in `data_pipeline/feeds.json`
  (stored as `papers.item_type = 'article'`, so search, saving and the assistant treat them like papers).
- **Raw first**: every response is archived unchanged in MinIO (`raw-ingestion/{openalex,arxiv,rss}/...`).
- **Incremental**: `ingestion_state` holds a cursor per source / topic / feed (OpenAlex cursor, arXiv offset, RSS
  `ETag` / `Last-Modified`); known IDs, DOIs and arXiv IDs are skipped before embedding; each run is logged in
  `ingestion_runs`.

## 8. Evaluation Framework & Benchmarks

Every number below is produced by `evaluation/evaluate_all.py` against the code the application runs: the search
SQL (`backend/services/search_service.py`), the recommendation formula (`recommendation_service.py`), the spam
model (`spam_service.py`) and entity resolution (`data_pipeline/dedup.py`). Labels come from
`evaluation/ground_truth.json`, rebuilt from the seed's planting rules (never from detector output), plus a manual
audit of real duplicates (`evaluation/dedup_audit.json`). Tunable settings are chosen on a development split and
reported on held-out data; 95 % intervals are bootstrap intervals (1,000 resamples).

```bash
python evaluation/build_ground_truth.py   # labels from the database + seed rules (seed_labels.json)
python evaluation/evaluate_all.py         # writes evaluation/evaluation_results.json (~10 s)
```

> [!NOTE]
> **Honest findings for the report.** (1) A PageRank prior cannot raise these relevance judgements (they measure
> topical match, not authority) and the citation graph is sparse, so PageRank is kept for tie-breaks, the prestige
> tier and featured papers. (2) The recommendation hybrid ties item-CF on held-out members and keeps working for new
> members (no co-saves → content only); with 28 members per split the differences are within noise. (3) A
> one-feature baseline beats the Isolation Forest on PR-AUC because the planted spammers differ mainly in volume,
> and the threshold is unstable: the 24 Nov run (with 15 leftover test accounts in the population) gave P 0.83 /
> R 1.00 at 0.09. Every flag goes to an admin review queue; in deployment the threshold should come from those
> confirm / clear decisions. Full discussion: `docs/TECHNICAL_REPORT.md` §6.

**Where each number lives** in `evaluation/evaluation_results.json`: duplicates `F4_F5_entity_resolution`; search
`F5_unified_search`; PageRank `F5_pagerank_validation`; recommendations `F6_recommendations`; spikes and spam
`F7_trends_and_spam`; assistant `F8_assistant_retrieval`. The "also saved" coverage was measured by calling
`/api/papers/{id}/also-saved` for every library item (25 Nov 2026).

**API tests:** `python -m pytest backend/tests -q` runs 32 end-to-end tests against the development database; the
throwaway accounts they create (`@tests.crc.invalid`) are deleted with everything they made.

## 10. Quick Start Guide

### Option A: one command (after the first-time setup below)

```bash
python start.py                     # starts the containers, checks the schema and model, runs backend + frontend, opens the browser
python start.py --separate-windows  # backend and frontend in their own terminals
python start.py --stop              # stop everything
```

### Option B: step by step (first-time setup and full reproduction)

**Step 1: Configure and start the infrastructure**
```bash
cp .env.example .env                # then set the passwords, CRC_AUTH_SECRET and CRC_DEMO_PASSCODE
docker compose up -d postgres minio ollama
```

**Step 2: Python environment**
```bash
python -m venv .venv
.venv\Scripts\activate              # Windows (macOS/Linux: source .venv/bin/activate)
pip install -r backend/requirements.txt
```

**Step 3: Schema and seed corpus**
```bash
python db/apply_migrations.py                    # schema.sql changes + migrations 002–009
python data_pipeline/seed_database.py            # OpenAlex/arXiv papers, synthetic community, planted ground truth
python data_pipeline/improve_data.py             # realistic names, comments and votes
python -m data_pipeline.fix_post_papers --apply  # attach seeded posts to papers on their own topics
```
*Downloads the embedding model, fetches papers, archives raw responses to MinIO and seeds PostgreSQL. Seeding
wipes the application tables, so do not run it on a database with real accounts.*

**Step 4: More content (optional but recommended)**
```bash
python data_pipeline/ingest.py                   # next batch from OpenAlex, arXiv and RSS, with entity resolution
python data_pipeline/enrich_citations.py         # OpenAlex citation counts + reference edges
```

**Step 5: Warehouse, PageRank and alerts**
```bash
python data_pipeline/run_dw_elt.py
```

**Step 6: Reproduce the evaluation**
```bash
python evaluation/build_ground_truth.py
python evaluation/evaluate_all.py                # → evaluation/evaluation_results.json (section 8)
python -m pytest backend/tests -q                # 32 API tests
```
*OpenAlex returns slightly different results over time, so a fresh seed gives slightly different counts and scores.*

**Step 7: Language model for the assistant**
```bash
docker exec -it crc_ollama ollama pull llama3.2:3b
```

**Step 8: Run the app**
```bash
uvicorn backend.main:app --host 0.0.0.0 --port 8000 --reload --reload-dir backend   # from the repo root
cd frontend && npm install && npm run dev                                             # http://localhost:3000
```

**Sign in:** seeded accounts use `memberN@chanakyauniversity.edu.in` (or university ID `24CU1000` + N − 1) and the
passcode you set in `CRC_DEMO_PASSCODE`. `member1` (`24CU1000`) is the administrator.

### Updating an existing database (instead of re-seeding)

One command applies every migration, the six-school mapping, member names, varied comments, votes and the warehouse
rebuild, without wiping data:

```bash
python db/update_database.py            # add --update-emails for first.last@chanakyauniversity.edu.in
```

Then restart the backend and the frontend.

## 11. Environment Variables

All configuration comes from a `.env` file in the repository root. Create it from the template with
`cp .env.example .env` and fill in your own values. **Never commit `.env`**: it is listed in `.gitignore`, and
only `.env.example` (placeholders, no real values) is tracked.

| Variable | Purpose | Secret |
|---|---|---|
| `POSTGRES_USER`, `POSTGRES_DB` | Database user and name | |
| `POSTGRES_PASSWORD` | Database password | **yes** |
| `DATABASE_URL` | Connection string used by the backend and pipeline (host port 5434); contains the password | **yes** |
| `MINIO_ROOT_USER`, `MINIO_ENDPOINT` | Data-lake user and address | |
| `MINIO_ROOT_PASSWORD` | Data-lake password | **yes** |
| `OLLAMA_BASE_URL`, `OLLAMA_MODEL` | Local LLM address and model name | |
| `CRC_AUTH_SECRET` | Signs login tokens; a long random string | **yes** |
| `CRC_DEMO_PASSCODE` | Shared passcode of the seeded demo accounts | **yes** |
| `CRC_CORS_ORIGINS` | Frontend origins allowed to call the API | |
| `NEXT_PUBLIC_API_ORIGIN` | API address used by the frontend | |

The code stops with a clear message if a required value is missing. Generate secrets with
`python -c "import secrets; print(secrets.token_urlsafe(32))"`, and use fresh values for any shared deployment.
